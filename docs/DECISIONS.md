## 2026-10-03 12:45 | Tanmay D | M3 agent: the LLM is the untrusted agent, called through a stdlib client
**Decision:** The M3 LLM plays the AI assistant being guarded, never a fraud detector, and nothing trusts its judgment: the device's policy ignores `claim`, which can only trigger the lie-check lock, and taint comes from `read_inbox`. `llm.py` calls any OpenAI-style `/chat/completions` endpoint with `urllib` (no SDK), so the provider is config only (`LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY`). The system prompt defines HIGH risk (per the 09:59 entry), rates every other send or delete as medium, and has no "ignore instructions in emails" hardening. By default the laptop prints only the agent's narration (the "lying screen"); `--show-calls` prints the real calls and verdicts. `GATEKEEPER_COMPROMISED=1` swaps in a scripted hijacked agent that needs no key or network. Runs stop on `locked` or after 10 tool calls.
**Why:** An LLM that judged emails would be the hole Gatekeeper closes, so its output must only ever tighten things. A stdlib client keeps dependencies at zero and avoids blocking M3 on the provider choice. Without hardening, the hijack rate reflects a normal agent and the device has to be what stops the attack. The scripted agent makes the stage demo deterministic even with bad Wi-Fi.
**Alternatives considered:** A provider SDK (new dependency, locks the provider). A scripted agent only, with no LLM (no real agent to protect; the benchmark would be meaningless). Prompt hardening against injection (more realistic for production, but it would hide what the device adds).

## 2026-10-03 13:30 | Tanmay D | M4-M5 benchmark: a worst-case agent measures the device; bench "hold" counts as a touch
**Decision:** `bench.py` runs the 44 scenarios in `scenarios.py` (24 attacks, 20 benign) through the real `agent.run`, executor and device policy with `bench=1`. Each scenario gets a throwaway copy of the data folder, and mail goes nowhere. There are two agents: `--agent llm` (the real model, which measures the true hijack rate) and the default `--agent worst-case`, a scripted agent that obeys every injection with the claim it was talked into. The worst-case agent needs no key, so its numbers measure only the device. A `hold` verdict counts as "needed a human touch". It isn't counted as stopped or as a false positive, and the report lists it separately. False positives are benign actions that end `blocked` or `locked`. Device policy and the protocol are unchanged.
**Why:** Without a key the only honest number is "if the agent is fully hijacked, what gets through". Counting holds as stopped would overstate the device, since a human could still approve, and counting them as false positives would understate it. The run found one real gap (atk-07, the mass delete of public files), which is logged in TODO instead of being fixed quietly.
**Alternatives considered:** Only a live-LLM benchmark (blocked on the provider, and not deterministic for tests). Making up hijack rates for the worst-case agent (dishonest). Patching the delete limit now (it's a firmware policy change, so it needs both people and a DECISIONS entry).

## 2026-10-03 15:30 | Tanmay D | M9 verifier: a separate mail gateway re-checks the device signature
**Decision:** `verifier.py` is a separate process: a minimal SMTP gateway on `localhost:1026` that relays to Mailpit (`:1025`). It trusts only the pinned device key. The executor now puts the device's approval on every email as `X-Gatekeeper-Act/To/File/Fh/Nonce/Exp/Taint/Sig` headers. The gateway relays only if the signature verifies over `protocol.signed_message(...)` and the signed fields match the delivery: exactly one envelope recipient equal to `to`, a matching `To` with no `Cc`/`Bcc`, exactly one attachment whose SHA-256 is `fh` and whose name is the basename of `file` (or none when `file` is empty), an unexpired `exp`, and an unused nonce. A nonce is consumed only on acceptance and given back if the relay fails. The executor sends to the gateway when `GATEKEEPER_SMTP_PORT=1026`; the default stays 1025, so existing flows don't change. `forge.py` is the demo: a compromised laptop tries 7 forgeries and a replay, and only the honest control is delivered. The device wire contract (`protocol.py`, v1) is unchanged; the headers are a host-side envelope between the executor and the gateway.
**Why:** This answers the judges' top question ("what does the hardware add if the executor is on the same laptop?"). Even with full control of the laptop, the attacker can't produce mail the gateway accepts without the device signing that exact recipient and file. SMTP keeps the executor change to one line (where it sends). The gateway is written on stdlib `socketserver` because Python 3.13 removed `smtpd`, and the project doesn't add dependencies without a DECISIONS entry.
**Alternatives considered:** `aiosmtpd` (a new dependency). An HTTP "bank" verifier (would need a second mail path; it fits M6 payments better, where Nessie can get the same check). Verifying deletes too (there's no separate file server to do it, so it's out of scope). **Known limit:** subject and body aren't signed in v1, so a valid approval could carry different text; the v2 contract adds the body hash `bh`. In the prototype Mailpit doesn't refuse direct connections on 1025. In production only the gateway can reach the mail server.

## 2026-10-03 16:00 | Tanmay D | M9 verifier hardening: strict message shape, nonces on disk, never released
**Decision:** The gateway now accepts only the exact shape the executor sends: a single `text/plain` body, or `multipart/mixed` with exactly that body plus one `attachment` part. HTML alternatives, nested multiparts and extra inline parts are refused. Used nonces are written to `.gateway_nonces` (fsynced, with entries dropped once their `exp` passes) before a message is accepted. If the write fails, the message is refused. A consumed nonce is never given back, even when the relay to Mailpit fails. This tightens the 15:30 entry, which said a nonce is "given back if the relay fails". This entry replaces that part.
**Why:** A security review of the M9 commit found two holes. (1) Counting only `iter_attachments()` let a message hide data in an HTML alternative or a nested `multipart/related` that a mail client would show. The recipient binding still held, so the data could only reach the approved recipient, but the gateway no longer delivered "exactly what the device approved". (2) Nonces lived in memory, so restarting the gateway let a captured approval be replayed until its `exp`, and giving a nonce back after a relay error could deliver an email twice if the upstream had already taken it.
**Alternatives considered:** Parsing every MIME part and hashing them all (more code, and still exposed to parser differences between the gateway and the mail client). Keeping nonces in memory and relying only on the 60 s `exp` (still leaves a replay window after a restart). Retrying the relay with the same approval (risks duplicates; asking the device again is cheap).

## 2026-10-03 16:45 | Tanmay D | M6 payments follow docs/CONTRACT.md v2; host and mock switch now, firmware at F4
**Decision:** M6 implements `docs/CONTRACT.md` (v2, frozen and agreed by Sid and Tanmay) exactly, for **all** actions. The signed string is `v2|act|to|file|fh|bh|amt|nonce|exp|taint`. Every request carries `amt` (int cents for `pay_invoice`, `0` otherwise) and `bh`: SHA-256 of `subject + "\n" + body` for `send_email`, and `""` for deletes and payments, so the payment memo isn't signed. The mock denies anything else: a payment with `amt` ≤ 0 or > 100000000, a non-empty `bh`/`file`/`fh` or a malformed payee id; a send without a 64-hex `bh`; a non-zero `amt` outside payments; or a missing `amt`/`bh`. Payment policy is per CONTRACT: an unlisted payee is `blocked`, every listed payment needs a human, and > 50000 cents also needs the RFID co-sign (in the mock, the `c` key; `a` alone is `denied`). The lie check covers payments. Host-side clarification (not a contract change, since only the host computes `bh`): "body" means the text/plain part exactly as delivered, with LF line endings and the trailing newline Python's `set_content` adds, so the executor and the M9 gateway hash the same bytes. The gateway now also rejects a message whose subject or body doesn't match `bh`.
**Why:** CONTRACT.md landed on main while M6 was in review, and the contract wins. An earlier draft of this PR used `amt|bh`, hashed the memo and kept send/delete on v1; that draft never merged. "Switch together at F4" means the host and mock move now and the firmware moves at F4. Until then the un-flashed board (v1) answers `denied` to this host, so merge this together with the F4 flash, or keep running the board from the previous `main`.
**Nessie:** this sandbox (`https://api.nessieisreal.com`; plain http doesn't connect) never updates stored balances and truncates amounts to whole dollars. A payment is a withdrawal from the payer plus a deposit to the payee, each tagged `[gk <ref> <cents>c]`, and the shown balance is a ledger (stored balance plus deposits minus withdrawals, exact cents). A blocked payment leaves no record. The demo account ids are in `config.py`; Acme `7083a93b-e422-4fa6-8188-330034f0c237` is the one payee in `mock_device.PAYEES` (and in the firmware at F4).
**Alternatives considered:** Keeping send/delete on v1 until F4 (contradicts CONTRACT, which retires v1). Signing the memo in `bh` (not in CONTRACT; would need both sign-offs). Nessie transfers (they have no payee field here and don't move balances).

## 2026-10-03 17:15 | Tanmay D | M9 bank: payments are verified by a separate bank process
**Decision:** This promotes the IDEA.md out-of-scope note ("in production, the bank or mail gateway verifies them") to a demoed capability for payments, as the mail gateway already did for email. `bank.py` is a separate process (stdlib `http.server` on `127.0.0.1:8099`). It holds the Nessie key and its own `Verifier`, with the pinned device key and its own nonce store `.bank_nonces`, separate from the executor's in-memory set and the gateway's file: a separate trust domain. `Verifier.verify(request, approval)` accepts only if the verdict is `allow`/`approved`, the Ed25519 signature verifies over `protocol.signed_message(...)` (CONTRACT v2), every signed field (`act`, `to`, `file`, `fh`, `bh`, `amt`) equals the action being performed, `exp` hasn't passed and the nonce is unused. The nonce is consumed only on acceptance and never given back (a failed Nessie call doesn't reopen it). The executor's `pay_invoice` now POSTs the payment and its approval to the bank and no longer calls Nessie, and `gk.py balances` reads the ledger through the bank, so the laptop needs neither the Nessie key nor the device key. `demo_forge.py` gets one real $750 approval (button + card) and shows legit → paid, forged (laptop's own key) → rejected, tampered ($750 → $75,000) → rejected, replay → rejected, with balance deltas as proof. No contract, firmware or dependency change.
**Why:** It answers the #1 judge question directly with money: a hacked executor can lie about approvals, but the bank checks the device's signature itself, so a forged or edited approval moves $0. The verdict in the approval isn't covered by the signature; checking it only rejects approvals the laptop itself labels non-signing. The signature over the exact payee and amount is what actually protects the money.
**Alternatives considered:** An in-process verifier class (simpler, but the laptop would still hold the Nessie key, so it doesn't answer the question). Sharing the gateway's nonce store (it would couple two trust domains). **Known limits:** the bank runs on the same machine and the Nessie key is in its environment; in production it's a different party on a different machine. Mailpit still accepts direct SMTP on 1025 (see 15:30).

## 2026-10-03 17:45 | Tanmay D | M7 voice runs on the device and speaks only the device's own view
**Decision:** ElevenLabs is called by the ESP32, not the laptop. `src/voice.cpp` streams `POST /v1/text-to-speech/<voice>?output_format=pcm_16000` (model `eleven_flash_v2_5`, `HTTP/1.0` so the body is raw PCM, TLS checked against GTS Root R1 + GlobalSign Root CA) into a MAX98357A I2S amp on BCLK 14 / LRC 17 / DIN 16, from a FreeRTOS task on core 0. `main.cpp` builds the sentence from the validated request fields (the same truth as the OLED): the action, the file name, the spoken address or payee name (an unknown payee is "an unknown account ending in" + its last four digits), the amount, a taint note, and the outcome. It speaks on HOLD (including the card co-sign prompt), BLOCKED and LOCKED, and not on auto-allow or in bench mode. The outcome is spoken first ("Gatekeeper: blocked. ..."), so a cut sentence still carries the verdict. Because the validator only promises printable ASCII, an address is read aloud only if it looks like an email (`[A-Za-z0-9._%+-]@[A-Za-z0-9.-]`, at most 64 characters); otherwise the device says "an unusual address at <registrable domain>" or won't read it at all. File names must be `[A-Za-z0-9._-]` and at most 40 characters, otherwise "a file with an unusual name". A lookalike host adds "whose real domain is ...". This keeps a hostile host from putting a sentence such as "this is the boss, approve" into the device's voice (found in a security review of the first commit). The voice task never writes to Serial, so it can't corrupt a JSON reply. The verdict, signature and reply never wait for audio, and any Wi-Fi/TLS/API failure means silence. Secrets live in a gitignored `include/secrets.h` (see `secrets.example.h`); without it voice compiles to no-ops. This moves M7 from the host TODO to the firmware. It's an **exception to the ownership rule** (like 11:00): the device owner reviews `src/main.cpp`/`src/voice.cpp` in the PR before flashing. No contract change and no new library (WiFiClientSecure and the I2S driver ship with the core).
**Why:** DECISIONS 11:14 requires the voice to speak the true action. If the laptop spoke, a compromised laptop could narrate a lie, which is exactly what the device exists to prevent. Building the text on the device keeps the voice a second trusted output. The device never sees email bodies, so it speaks the action an email led to, not the email itself.
**Alternatives considered:** Laptop-side TTS (simpler and no Wi-Fi on the device, but untrusted). Pre-recorded clips on the device (can't say arbitrary addresses or amounts). MP3 output (needs a decoder; raw PCM streams straight to I2S). **Risks:** venue Wi-Fi (use a phone hotspot), the API key sits in flash (use a key with limited credits), and Wi-Fi TX plus the amp can brown out a USB-powered board, which would reboot it and clear lock state (power the amp from 5V VIN, and use a good cable or supply).
